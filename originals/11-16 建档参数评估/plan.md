# 日档与知识库患者参数对照计划

日期：2026-11-16  
状态：用户已确认执行骨架；2026-11-16已完成3患者日与10知识单元试点，待审核清单及映射。详细发现见 review_notes.md。

## 1. 我们要弄清什么

知识库即使召回了正确规则，也可能因为患者信息不足而无法用于当前判断。我们先把两端的清单摆出来：`icu_daily_archive` 实际提供什么，知识库要求知道什么，再看它们差在哪里。

这一轮回答的是“参数种类能否对上”。“每个患者每天是否都有这些参数”“能否回答某道临床问题”留到后续。先分清这两件事，才能避免把一份很长的字段表当成患者信息已经充分的证明。

本次从日档出发，不从既有30题筛选参数，也不重新生成答案。

## 2. 为什么这样做

先独立整理两边，再取交集和差集。这样既能发现日档供给不足，也能发现知识库需求漏标，不会默认其中一边就是标准答案。

有三个容易误判的地方，决定了清单不能只写参数名称：

- 信息可能藏在叙述文本里。没有专门字段，不代表没有记录。
- 名称一样，要求可能不同。“肌酐”与“基线肌酐”、“尿量”与“过去6小时尿量”不能直接算匹配。
- 参数在某条日档出现过，只证明样本中存在这种信息，不能证明其他患者日也有。

因此首轮保留原名、位置、时间和含义，先核查小样本，再决定是否扩大。暂不计算一个混合的“完整率”：它会掩盖上述差别，也没有经过确认的临床分母。

## 3. 第一步：整理日档实际保存的参数

### 先看结构，再选3个患者日

计划获批后，先读取表结构、字段说明及必要的记录日期概况，确认参数存放在普通列、JSON还是文本中。既有新鲜度核查只用于导航；如需使用当前日期范围，将重新只读查询，区分临床日期与写入时间。

随后选3个患者日验证盘点方法。根据实际记录，尽量包含常见内容形态、可关联连续日档的记录、内容较复杂或结构不同的记录。先记录选择依据，再展开内容核查；不按“资料看起来齐全”挑选，也不声称3例具有总体代表性。必要时查看相邻日档，用来辨认时间表达，并单列读取范围。

### 如何整理

逐条查看结构化字段、JSON内部键和叙述内容。参数不限于数值，也包括诊断、治疗状态、用药、支持措施、既往史等患者事实；这些只是观察方向，不预设数据库一定有这些栏目。

对每个发现的参数记录以下信息：

| 字段 | 用途 |
|---|---|
| 参数编号、原始名称、暂定统一名称 | 便于归并，同时能回到原文 |
| 含义及类别 | 分清患者事实、治疗记录与管理字段 |
| 表字段／JSON路径／文本片段定位 | 说明在哪里找到 |
| 表达形式、原始单位 | 区分数值、类别、自由文本及单位缺失 |
| 事件时间、时间窗口及其清晰程度 | 分清当天、既往、累计量与日期不明 |
| 脱敏示例、证据编号 | 让发现可以复核 |
| 样本出现情况与记录状态 | 分开记录有值、空值、占位、明确未测、明确否定、含义不清 |

先把“字段存在”和“有效内容存在”分开。空字段不算已提供；“未记载”不解释成正常、没有发生或没有实施。需要计算才得到的指标单列为“可派生候选”，保留所需输入，不冒充日档已存值。

本步产出：日档参数清单 v0.1，明确标注3个患者日的样本范围、读取日期和未解析内容。

## 4. 第二步：整理知识库需要的患者参数

先定位实际使用的正式知识库文件，记录版本或文件哈希、记录数量与状态筛选规则，不沿用历史数量。优先盘点当前有效知识单元的 `param_requirements`，退役或停用记录另计，不混进当前需求。

先取10个知识单元检查字段形态和提取方式，兼顾数值、时间、治疗状态或条件性需求。方法核对无误后，可做既有字段的全量离线枚举；正文语义核验仍从这10个单元开始，不能把字段已提取写成正文已核验。

| 字段 | 用途 |
|---|---|
| 需求编号、原始名称、暂定统一名称 | 与日档清单对照 |
| 知识单元ID、标题、状态 | 保留需求来源及适用范围 |
| 正文相关片段及位置 | 检查需求有没有正文依据 |
| 参数用途、时间窗口、适用条件 | 说明知识为什么需要它 |
| 提取来源、正文核验状态 | 区分既有标注和本次核验判断 |
| 疑点与待确认事项 | 容纳歧义、漏标及可能误标 |

重点检查：有没有把指南阈值误当患者参数；有没有遗漏基线、持续时间等限定；有没有仅在特定条件下才需要的参数。临床必要性不确定时标“待医生确认”。正文发现的新需求以候选形式另列，本轮不写回正式知识库。

## 5. 第三步：做交集和两侧差集

归并名称时保留原名和理由。明确同义词可以合并；基线与当前、单次与累计、医嘱与实际实施分别保留。单位可换算也不等于直接可用，需记录换算条件；有歧义的映射先留待确认。

对照表保留两端编号、匹配状态、匹配依据、时间／单位／粒度差异、核查范围和下一步动作。

| 对照结果 | 如何解释 | 下一步 |
|---|---|---|
| 两边都有，含义及限定一致 | 样本中找到对应表达 | 后续检查具体患者日能否使用 |
| 两边都有，但只能部分对应 | 名称相近，时间、单位或条件不同 | 明确还差哪个限定，避免算成完全匹配 |
| 知识库需要，日档样本未找到 | 当前样本未见，不等于全表不存在 | 先检查文本与别名，再决定扩大查找或追溯源记录 |
| 日档有，知识库需求未列 | 可能是背景信息，也可能需求漏标 | 查对应知识用途，保留两种解释 |
| 无法确定对应关系 | 现有证据不足以归并 | 列出具体歧义供讨论 |

本轮不做全面源记录追溯。若需要解释重要缺口，先列出待查来源与理由。未实际检查源记录，就标“源记录层未核查”，不归因为源头缺失或日档整理遗漏。

## 6. 我们会看到什么，如何讨论

结果先交两张清单和差异表，再逐节形成一页发现：

1. **问题与假设**：两端可能在哪里对不上，哪些只是待验证想法。
2. **设计理由**：为何先独立盘点、为何保留时间和粒度。
3. **中间观察**：实际遇到的隐藏信息、名称歧义或需求误标；这些发现如何改变判断。
4. **结果**：样本中确认了哪些对应关系，哪些仍有差异。
5. **归因与讨论**：优先追查哪几个缺口，需要什么新证据。

讨论重点是几个能改变下一步行动的差异。例如，如果信息已在文本里，下一步可能是改善提取；如果需求标注漏了时间窗口，下一步应先修订需求候选；如果当前样本没有，就需要扩大核查，而不是直接要求补建档。

以上为解释路径示例，不是本批已发现的问题。
