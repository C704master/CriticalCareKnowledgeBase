## 1. Python 准备输入：给原字符串编一个能查回去的键

用户原题是“患者嗜睡的原因是什么”。资料已经保存在本地。Python 先按换行给病历编号，再按句号、分号切短，在每一行内部从 1 开始编号。原始格式是一个字典，键指向原文。下面是 F24 请求里真实存在的两个条目（另两条涉及另一种药，暂略）：

```json
{
  "P20.78": "22:00 艾司唑仑2mg。",
  "P30.51": "[艾司唑仑片(舒乐安定)] 21:00 1mg；"
}
```

P20.78 的意思是**原输入第 20 行切出来的第 78 段**。20 是行号，不是日期。日期放在这一行所属的栏目标题里。程序顺序扫描原始行，碰到新标题就更新当前标题，后面的行沿用它。这样第 20 行对应 10 月 21 日的执行栏目，第 30 行对应 10 月 22 日的执行栏目。此处并没有把药物抽取成四个数据库字段；实际保存的是**可回查的编号、栏目标题、原文字符串**。[输入逐行编号](code/%E5%9B%9E%E7%AD%94%E5%89%8D%E9%80%82%E7%94%A8%E6%80%A7%E8%AF%95%E9%AA%8C/%E4%B8%89%E4%BE%8B%E6%89%A9%E5%B1%95_F27_F24_F29/paired.py) · [切片与建字典，见 chunks 和 run](code/%E5%9B%9E%E7%AD%94%E5%89%8D%E9%80%82%E7%94%A8%E6%80%A7%E8%AF%95%E9%AA%8C/%E4%B8%89%E4%BE%8B%E6%89%A9%E5%B1%95_F27_F24_F29/question_first.py)

## 2. Qwen 写草稿：“候选答句”从这里来

代码先发一个只含问题的病例任务，让 Qwen 写通用核查要点。接着 Python 把**问题、截止点、通用要点、病历片段字典、知识片段字典**装进第二个请求，阶段名叫 compose。提示要求 Qwen 写二至四条，每条给出一句内容和支持它的片段编号。编号候选来自 Python，**用哪些编号、怎样组织句子，是 Qwen 生成的**。

这次 compose 的首次原始输出是一个有四个对象的 JSON 数组。第三个对象才是本篇说的“候选答句”。下面是它的实际内容：

```json
{
  "类型": "待核实",
  "内容": "患者10月21日及22日均使用艾司唑仑及酒石酸唑吡坦等镇静催眠药物，需核实用药时间与嗜睡程度的关联，以排除药物性镇静过度导致的意识抑制。",
  "病历片段": ["P20.78", "P20.83", "P30.51", "P30.52"],
  "知识片段": ["E3.1", "E5.1"]
}
```

也就是说，候选答句只是**程序下一步要送审的一条模型草稿**。它说两晚用过药，病因还要核实。**此时草稿没有写“21 日 1 mg”。**

这里有一个读源码才看得出的细节：V7 写稿程序对首次输出报过“正文含日期数值”的格式错误，后面还有修复轮。这个 F24 实验的逐句审稿脚本明确从 **V7 首次 compose 响应**读取数组，因此追这条错句要从那份原始 JSON 开始，单看 V7 最终排版的答案会对不上。[写稿实际请求 · 来源记录](sources/02.md#s01) · [写稿首次响应（第三个对象） · 来源记录](sources/02.md#s02) · [首次格式检查 · 来源记录](sources/02.md#s03)

## 3. Python 挑材料，Qwen 再审一次：错误在这里出现

Python 对四个对象逐个调用审稿函数。第三条落在 claim_03。程序从字典里拿出该句点名的四条病历原文，附上同一行的相邻片段、所选知识和原题，组成一次新的 verify 请求。Qwen 的任务是选择“保留／改写／删除”，并返回能进正文的一句话。这次调用实际收到的四条给药短句本身只有时刻、药名和剂量；患者日档的日期标题由程序另行保存，不能把系统掌握的标题都当作这一组短句里已经明写的内容。

Qwen 选择了“改写”，又在新句子里补写了两晚各用多少药。只对比其中一种药：

| 日期 | Qwen 审稿时新写出的说法 | Python 按所引编号能取到的执行记录 |
|---|---|---|
| 10 月 21 日 | 21:00，1 mg | P20.78：**22:00，2 mg** |
| 10 月 22 日 | 22:00，2 mg | P30.51：**21:00，1 mg** |

**这就是出错的位置：草稿本来只说“这两天用过药”，审稿模型试图把它写得更具体，结果把两晚对调了。** 这能从两次模型响应的差异确认。仅凭日志无法断定模型内部为什么选错对应关系。[送审时实际给了什么 · 来源记录](sources/02.md#s04) · [审稿 Qwen 的改写原话 · 来源记录](sources/02.md#s05) · [怎样组装审稿请求](code/%E5%9B%9E%E7%AD%94%E5%89%8D%E9%80%82%E7%94%A8%E6%80%A7%E8%AF%95%E9%AA%8C/%E4%B8%89%E4%BE%8B%E6%89%A9%E5%B1%95_F27_F24_F29/claim_review.py)

## 4. Python 处理改写：条件分支，然后查字典

审稿模型的返回也只是一段 JSON。Python 先解析它，检查引用编号在允许的范围里，再把返回对象交给 validate_record_claim。下面是源程序中决定这条给药答句走哪条路的两行：

```python
orders = [k for k in keys if context[line_number(k)][1] == "orders_execution"]
if orders and DOSE_OR_TIME.search(body):
```

第一行筛出引用中属于“医嘱执行”的编号；第二行判断编号列表非空，且正文中有时刻或剂量形式的文本（如 21:00、1mg）。两项都满足，程序就**不用模型自由复述的给药细节**，把本次正文改成：

> 具体给药时间和剂量见所引执行记录。需核实嗜睡发生的具体时点及程度，以评估药物镇静作用。

接着排版程序对每个引用编号做的核心操作是 **取标题 + 编号 + 原文**。以 P20.78 为例，标题取第 20 行所属栏目，原句取字典中 P20.78 的值。最终给读者看的两行是：

```text
【2026-10-21 orders_execution】 P20.78　22:00 艾司唑仑2mg。
【2026-10-22 orders_execution】 P30.51　[艾司唑仑片(舒乐安定)] 21:00 1mg；
```

程序没有再请 Qwen 猜哪天用了几毫克，也没有为这句话逐项生成“日期错误／剂量错误”的诊断。**即便模型写对了，只要上述两个条件为真，也会走同一个照录分支。** 好处是时间和剂量始终待在原片段里。局限是如果模型一开始选错了记录编号，还要另查引用是否相关。[分支和改写规则](code/%E5%9B%9E%E7%AD%94%E5%89%8D%E9%80%82%E7%94%A8%E6%80%A7%E8%AF%95%E9%AA%8C/%E4%B8%89%E4%BE%8B%E6%89%A9%E5%B1%95_F27_F24_F29/record_guard.py) · [本句实际触发的动作 · 来源记录](sources/02.md#s06) · [最终排版时如何读取字典](code/%E5%9B%9E%E7%AD%94%E5%89%8D%E9%80%82%E7%94%A8%E6%80%A7%E8%AF%95%E9%AA%8C/%E4%B8%89%E4%BE%8B%E6%89%A9%E5%B1%95_F27_F24_F29/anchored.py)

## 5. 我们怎么知道代码真的这么跑过？

回放脚本复用已保存的 Qwen 响应，重新执行 Python 的规则和排版，新增模型调用为零。针对第三句，它检查改写结果里已经没有错配的“10月21日21:00”，仍保留“需核实嗜睡发生的具体时点”，并检查带准确日期和剂量的两条执行原句确实出现在输出中。另用删除首日、中间日、末日材料的反例测试连续观察，这是同一回放中的另一项检查。

## 6. 修复后重试：Qwen 自己能改对哪一天？

这一次我们主动把错句交给审稿模型，提前写下通过条件：模型要指出 1 mg 属于 10 月 22 日，并拒绝候选句里的 21 日。评分看 Qwen 的原始回复，位置在 Python 照录保护之前。

| 跟着一条记录看 | 本次实际内容 |
|---|---|
| 人预先放入的错句 | 10月21日21:00使用艾司唑仑1mg。 |
| 修复后 Qwen 收到的 P30.51 | 【2026-10-22 orders_execution】 [艾司唑仑片(舒乐安定)] 21:00 1mg； |
| Qwen 选择的动作与引用 | **改写**，引用 **P30.51** |
| Qwen 返回的答句 | 10月22日21:00使用艾司唑仑1mg，嗜睡原因待核实。 |

**本例通过。** Qwen 的理由原话是“候选日期错误，实际为10月22日”。因此可以把纠正日期记为模型完成的动作。它把嗜睡原因留作待核实，本次只对日期纠错评分。
